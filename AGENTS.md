# Repository Guidelines

This repository is the planning and implementation workspace for a local n8n vendor certificate-of-insurance (COI) chasing demo. Treat it as an automation project, not a compiled app. The core behavior will live in n8n workflow exports, Postgres schema/state, fixtures, and small helper scripts.

`AGENTS.md` and `CLAUDE.md` hold the same guidance for different agents. Keep them in sync.

## Read Order And Authority

Read these files before changing scope or implementation details:

1. `build-plan.md`: staged plan to follow across sessions.
2. `progress-notes.md`: current status, completed stages, deviations, and open items.
3. `coi-demo-build-plan.md`: detailed controlling implementation spec.
4. `01-vendor-coi-chase.md`: validated problem and architecture rationale.
5. `foundation-1-vendor-insurance.md`: domain background only.

If documents conflict, prefer the newest decision recorded in `progress-notes.md`, then update the stale document instead of silently guessing.

## Project Structure

Implementation directories:

- `n8n-workflows/`: importable n8n workflow JSON exports, generated by `scripts/generate-stage-*` rather than hand-edited.
- `db/postgres/`: schema, migrations, seed SQL, and reset SQL.
- `scripts/`: local setup, import, reset, validation, and fixture helpers.
- `fixtures/`: synthetic COI PDFs, email payloads, and expected outputs.
- `docs/`: runbooks, prompt schemas, demo notes, marketing content plans and scripts, and production caveats.
- `.agents/`: shared context that marketing and writing skills read before acting. `product-marketing.md` holds positioning, audience, banned vocabulary, and voice; update it there rather than restating positioning per task.

Use lowercase hyphenated filenames. Use `snake_case` for database columns and JSON fields unless an external API requires otherwise.

## Local Services And Commands

General repository commands:

- `rg --files`: list repository files.
- `git status --short`: check the worktree before edits.
- `git diff -- *.md`: review documentation changes.
- `Get-Content -Raw <file>.json | ConvertFrom-Json | Out-Null`: validate a workflow JSON export.
- `docker images`: check available local images before adding or pulling new ones.
- `docker compose ps`: inspect local service status.
- `docker compose logs n8n`: inspect n8n startup/import/runtime failures.
- `n8n export:workflow --all --output=n8n-workflows/`: export workflows from a running n8n instance.

Stage scripts, run from the repo root with Docker running:

- `.\scripts\init-env.ps1`: generate local `.env` from `.env.example`.
- `docker compose config`: validate Docker Compose configuration.
- `.\scripts\start-local.ps1`: start local n8n, Postgres, and read-only pgweb.
- `.\scripts\verify-local.ps1`: verify Compose config, Postgres readiness/query, n8n HTTP availability, and pgweb HTTP availability.
- `.\scripts\apply-pgweb-viewer.ps1`: create/update the restricted `coi_readonly` Postgres user, expose only COI demo views in schema `coi_pgweb`, update local pgweb `.env` values if missing, and restart pgweb.
- `.\scripts\stop-local.ps1`: stop the local stack without removing volumes.
- `.\scripts\apply-stage-2.ps1`: apply the Stage 2 Postgres schema and synthetic seed data.
- `.\scripts\verify-stage-2.ps1`: verify Stage 2 tables, config, seed vendors, normalization, trade fallback, and empty certificate/outreach tables.
- `.\scripts\generate-stage-3-fixtures.ps1`: regenerate the synthetic Stage 3 fixture PDFs, email payloads, and expected metadata.
- `.\scripts\verify-stage-3-fixtures.ps1`: verify fixture counts, text layers, scanned/no-text behavior, password protection, forbidden terms, and rendered previews.
- `.\scripts\generate-stage-4-workflow.ps1`: regenerate the Stage 4 n8n workflow export from the shared validator and extraction schema.
- `.\scripts\verify-stage-4-validation.ps1`: run offline Stage 4 validator tests for deterministic flags and storage dispositions.
- `.\scripts\verify-stage-4-extraction.ps1`: validate the Stage 4 workflow JSON and, when n8n/Postgres are running, import and execute the fixed fixture smoke workflow.
- `.\scripts\generate-stage-5-workflows.ps1`: regenerate Stage 5 intake and source-document workflow exports.
- `.\scripts\apply-stage-5.ps1`: apply Stage 2 plus Stage 5 intake SQL and create today's local certificate storage directory.
- `.\scripts\verify-stage-5-storage.ps1`: run deterministic Stage 5 SQL/storage checks.
- `.\scripts\verify-stage-5-intake.ps1`: run live n8n/OpenAI Stage 5 fixture smoke checks and source-PDF route check.
- `.\scripts\generate-stage-6-workflows.ps1`: regenerate Stage 6 daily watch/chase and no-PDF reply workflow exports.
- `.\scripts\apply-stage-6.ps1`: apply Stage 2, Stage 5, and Stage 6 watch/chase SQL.
- `.\scripts\verify-stage-6-watch.ps1`: run deterministic Stage 6 bucket, suppression, escalation, reply notice, and manual override checks.
- `.\scripts\verify-stage-6-workflows.ps1`: validate, import, publish, and smoke-test Stage 6 workflow exports.
- `.\scripts\generate-stage-7-dashboard-workflow.ps1`: regenerate the Stage 7 dashboard workflow export.
- `.\scripts\apply-stage-7.ps1`: apply Stage 2, Stage 5, Stage 6, and Stage 7 dashboard SQL.
- `.\scripts\verify-stage-7-dashboard.ps1`: validate, import, publish, seed, render, and source-link test the Stage 7 dashboard workflow.
- `.\scripts\reset-demo.ps1`: reset the local demo to 18 seeded vendors, zero certificate/coverage/notice/outreach rows, clear Stage 6/7 date overrides, and create today's certificate storage directory.
- `.\scripts\verify-stage-8-fixtures.ps1`: regenerate/import/publish demo workflows, reset state, run Stage 8 fixture scenarios through the Stage 5 manual trigger, verify dashboard/source-link/watch behavior, write ignored raw output under `tmp/`, update `docs/stage-8-fixture-results.md`, and leave the demo reset. Add `-IncludeLiveEmail` to send a real Stage 6 Gmail approval email after the fixture suite, or `-OnlyLiveEmail` to run just the opt-in Gmail approval/send rehearsal.
- `.\scripts\verify-stage-9-production-readiness.ps1`: verify Stage 9 production-readiness documents exist and cover hosting, n8n licensing, error alerts, retry/backoff, dead letters, idempotency, heartbeat, canary, digest, uptime, backup/restore, scope limits, data retention, onboarding, and exit/export.
- `.\scripts\generate-linkedin-carousel.ps1`: render the LinkedIn document carousels in `docs/carousels/` to upload-ready PDFs in `docs/carousels/out/`. Add `-Name <file-stem>` for a single carousel.

Expected local services are n8n at `http://localhost:5678`, read-only pgweb at `http://localhost:8081`, and Postgres on `127.0.0.1:5432`. Gmail/OpenAI credentials are created manually inside n8n and must not be stored in repo files. One Gmail or Google Workspace mailbox is enough for local testing; use plus-address aliases for logical vendor, producer, approval, and intake roles when needed. Do not assume Docker images, accounts, OAuth apps, API keys, or n8n credentials already exist. On first n8n 2.x startup, internal migrations can take long enough for early HTTP probes to fail; rerun `.\scripts\verify-local.ps1` or rely on its retry loop. The `n8nio/n8n:latest` image may log a Python task-runner warning because Python is absent; this is not a Stage 1 blocker when JS workflows and service health pass. pgweb should lock to `coi_readonly` and schema `coi_pgweb`; if it shows n8n internal tables, run `.\scripts\apply-pgweb-viewer.ps1` and hard-refresh the browser session.

For n8n 2.29 CLI smoke tests, `n8n execute --file` is deprecated and may still require `--id`; import temporary smoke workflows into the local project, execute them by ID, then delete the temporary workflows from n8n. Running `n8n execute` inside the active n8n service container can collide with the task broker port; prefer `docker compose run --rm --no-deps n8n execute --id <workflow-id> --rawOutput` for repeatable smoke scripts. n8n 2.29 does not expose `delete:workflow`; temporary workflow cleanup can delete the known smoke workflow ID from Postgres.

Some PowerShell 5.1 sessions prepend a UTF-8 BOM when piping a string into a native command's stdin. `psql` tolerates it, but `n8n import:workflow` fails with `Unexpected token '﻿'`, and the import helpers in the verify scripts delete a workflow before importing, so a failed run can leave a demo-facing workflow missing from n8n. Setting `[Console]::OutputEncoding` does not suppress it. Check the repo files first with a hex dump; if they are clean, pipe the import through the Bash tool instead, then republish and restart n8n. Also avoid `2>&1` on these scripts: it turns `psql` NOTICE output into a terminating `NativeCommandError` and aborts the run early.

Demo-deliverable top-level workflows are not temporary artifacts. Keep each demo-facing workflow export imported into n8n and published after implementation so it is visible in the UI with its execution history. Do not keep extra proof harnesses, experiments, or throwaway smoke workflows in n8n after verification; keep those as repo exports/scripts only. Cleanup scripts may remove throwaway smoke workflows, but must not delete demo-facing workflow IDs such as Stage 5 intake or source-document routes.

Stage 2 SQL scripts are applied by piping them into the running Postgres service with `psql -v ON_ERROR_STOP=1 -f -`. Keep Stage 2 seed SQL idempotent; rerunning it must not duplicate vendors, holder entities, trade requirements, or config rows.

Stage 3 fixture scripts use the bundled Codex Python runtime when available because system Python may not have PDF dependencies. Rendered fixture previews are generated under ignored `tmp/stage-3-previews/`; do not commit preview images unless a later task explicitly asks for visual artifacts.

Stage 4 keeps validation logic in `scripts/lib/coi-stage-4-validator.js` and embeds that shared source into the generated n8n workflow export. Edit the shared validator first, then rerun `.\scripts\generate-stage-4-workflow.ps1`; do not hand-edit the embedded validator code in `n8n-workflows/stage-4-extraction-validation-core.json`. The generated workflow uses n8n OpenAI node V2 with `resource: text`, `operation: response`, `responses.values`, and JSON Schema under `options.textFormat.textOptions`; older `operation: message` examples do not import correctly on n8n 2.29. File read and extract nodes can strip JSON context or binary data, so reattach fixture context and binary explicitly before model and validation nodes. `Extract From File` aborts password-protected PDFs before downstream validation can run; route known encrypted fixtures around extraction to a structured review result.

Stage 5 stores source PDFs under `/home/node/.n8n-files/certificates/YYYY/MM/DD/`, mounted from ignored `./data/certificates`. n8n's file node requires parent directories to exist under its allowed-files area, so rerun `.\scripts\apply-stage-5.ps1` or create the current UTC date path before live upload tests. The source-document webhook export needs a stable `webhookId` and `triggerCount: 1`; after CLI activation, restart n8n for the route to register. In this n8n 2.29 setup the local source route is reached as `/webhook/stage-5-source-document-webhook/coi-source/<certificate_id>`.

Stage 6 keeps watch/chase state in Postgres functions and generated workflow exports. Empty Postgres result nodes that must allow downstream work, such as the escalation pre-pass before loading actionable vendors, need `alwaysOutputData`; otherwise n8n stops the execution when no rows are returned. Stage 6 live approval/send smoke requires both `stage_6_approver_email` and `stage_6_test_recipient_email`; they can be the same Gmail address for local testing. Stage 6 SQL defaults must preserve existing local config values on reapply so `apply-stage-6.ps1` does not wipe test email settings.

Stage 7 serves the dashboard through n8n webhooks at `/webhook/coi` and `/webhook/stage-7-dashboard-webhook/coi`. After CLI import/publish and n8n restart, wait for active workflow registration before probing the dashboard URL; editor HTTP readiness can come up before webhook routes are registered.

Stage 8 full fixture verification uses the Stage 5 manual trigger, not Gmail polling, for repeatability. The verifier keeps demo-facing workflows imported and published, writes raw n8n CLI output under ignored `tmp/stage8-intake-*.txt`, and may need to treat n8n Docker stderr warnings as output while still checking the native exit code. Use `.\scripts\verify-stage-8-fixtures.ps1 -IncludeLiveEmail` when a full rehearsal must send a real Gmail approval email, or `.\scripts\verify-stage-8-fixtures.ps1 -OnlyLiveEmail` when you only need to test approval/send; without either switch, no email should be expected. The live-email verifier reads the final Gmail message back by ID and records labels; when approver and test recipient are the same Gmail account, exact-subject All Mail search may be clearer than the Primary Inbox view. Manual fallback video/public mobile-data checks remain pre-live-demo checklist items, not script-enforced artifacts.

Stage 9 is a production-readiness planning stage, not a demo behavior stage. It documents the controls required before client reliance: single-client/client-owned hosting, licensing review, protected public surfaces, Error Trigger alerts, retries, dead-letter queue, message/attachment idempotency, heartbeat, canary, weekly digest, uptime checks, backup/restore testing, scope limits, data retention terms, onboarding, and exit/export. Do not describe the local Stage 5-8 demo stack as production-ready until those controls are implemented and tested for the target client.

LinkedIn carousels are HTML rendered to PDF at 1080x1350. `docs/carousels/README.md` is the controlling design system: owner-supplied palette and the rules for where each color may appear, the two typefaces, the graphic devices, and the standing layout rules. `docs/carousels/carousel-template.css` implements it and is shared by every carousel; per-post HTML supplies content and layout classes only, and must not introduce its own sizes, colors, or spacing. Add new layouts to the shared stylesheet so later posts inherit them. Do not reuse the Stage 7 dashboard colors here; that is a demo UI, not the brand. Rendered PDFs under `docs/carousels/out/` are ignored build output. Invoking `chrome.exe` directly from PowerShell hands the command line to an already-running Chrome, returns no exit code, and writes no PDF; use `Start-Process -Wait -PassThru` with a throwaway `--user-data-dir`. Webfonts load over the network at render time, so a failed fetch silently falls back to a system serif rather than erroring.

## Architecture Rules

- n8n orchestrates the workflow; Postgres is durable automation state.
- Do not use n8n Data Tables for core state.
- Gmail Trigger and Gmail nodes are the default email path for the demo.
- IMAP is only a disabled fallback for non-Google inboxes.
- SMTP/Send Email is only a generic fallback; it is not required for the Gmail demo path.
- Use n8n OpenAI node V2 by default for extraction and drafting.
- Use HTTP Request only if the OpenAI node cannot expose the required model, PDF file input, JSON schema output, or error-handling controls.
- Keep Telegram optional. Gmail-based human approval is the default approval path.
- Do not add OCR Bro as the default. Try text extraction first, then use the OpenAI PDF/file path when text is insufficient.

## n8n Workflow Rules

Prefer editable workflow JSON exports over manual-only UI changes. Name every node descriptively; never leave default names like `Code`, `If`, `Set`, or `HTTP Request`.

Use n8n credentials by name only. Never hardcode secrets, bearer tokens, OAuth client secrets, Gmail tokens, or OpenAI keys in workflow JSON.

Known n8n gotchas to account for during implementation:

- Active webhooks may use the active workflow snapshot, not the editor draft.
- After import or activation, verify with a real execution, database row, or validation script before treating the workflow as passed.
- Code nodes may be sandboxed; do not assume `process.env` exists.
- Optional Postgres update/cleanup nodes need `alwaysOutputData` if downstream nodes must continue after zero rows.
- Postgres nodes that update then reselect rows must return every field later expressions use.
- Form Trigger submissions can render fields as `field-0`; normalize form payloads before SQL or AI steps.
- AI structured output may be wrapped under `output`; downstream expressions should handle wrapped and direct JSON shapes.

## Testing And Verification

Validation scripts are the tests once implementation begins. Each stage should include a repeatable verification command and synthetic fixtures before moving on.

Minimum fixture scenarios:

- valid COI with all required coverage.
- expired policy.
- missing endorsement or coverage.
- wrong certificate holder.
- non-certificate attachment.
- low-text/scanned PDF.
- duplicate Gmail message or duplicate attachment replay.

Record completed checks and failures in `progress-notes.md`.

## Security And Configuration

Never commit `.env`, exported credentials, real vendor documents, real client data, Gmail OAuth secrets, OpenAI API keys, or production n8n exports containing secrets. Keep examples placeholder-only.

Before adding or pulling Docker images, check local images first with `docker images`. If a required image is missing, document the need and ask before pulling.

Build reset paths for local demo data only. Never run destructive reset/delete scripts against a client Gmail account, client database, or production workflow.

## Commit And Completion Guidelines

Use short imperative or conventional commits, matching existing history, for example `docs: update COI workflow guidance` or `feat: add intake preflight`.

Before every final response, run the agent-guidance maintenance checkpoint: decide whether the task exposed a durable mistake, blocker, workaround, command, gotcha, or best practice. If yes, update `AGENTS.md` and `CLAUDE.md` first, keeping both files consistent. Keep updates short, remove stale or duplicate wording, and prefer tightening existing rules over appending new sections.

If a task changes commands, scripts, workflow behavior, data model, implementation decisions, or durable repo rules, update the relevant documentation before finishing. Use `progress-notes.md` for stage status, deviations, verification results, and outstanding work. Update `build-plan.md` or `coi-demo-build-plan.md` only when the plan or controlling spec actually changes.

After every completed implementation task, commit and push the changes. If no remote is configured, commit is not requested, or push fails, report that clearly; include the commit hash if a commit was created. For documentation-only planning edits, do not auto-commit unless the user asks.

Pull requests should summarize the stage affected, verification performed, credential/manual steps, and any deviation from `build-plan.md`.
